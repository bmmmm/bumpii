# Contributing

## Setup

```console
$ gh repo clone bmmmm/bumpii && cd bumpii
$ pnpm install         # typescript, @types/node, biome — all dev-only
$ pnpm check           # tsc --noEmit
$ pnpm lint            # biome check
$ pnpm format          # biome check --write
$ pnpm test            # node:test
```

pnpm, not npm — a `preinstall` guard enforces it, and `pnpm-workspace.yaml`
carries the supply-chain settings (`minimumReleaseAge`, no install-time build
scripts) that npm would ignore. Node 24 is the floor: the sources are `.ts`
and run through Node's own type stripping, and `src/cli.ts` guards its
entrypoint with `import.meta.main`.

There is no build step. `bin/bumpii` runs `src/cli.ts` directly.

## The shape of the thing

One direction of flow, no cycles:

| File | Owns |
| --- | --- |
| `src/cli.ts` | Argument parsing, the subcommands, and the per-tool orchestration. The only place that decides an exit code. |
| `src/config.ts` | Reading, validating and rewriting `~/.config/bumpii/tools.json`. |
| `src/sources.ts` | Talking to a forge. Two API shapes: GitHub's and Forgejo/Gitea's. |
| `src/version.ts` | Probing an installed binary, and all version comparison. |
| `src/judge.ts` | Choosing an engine and turning release notes into structured items. |
| `src/usage.ts` | Grepping your own files for the commands a change touches. |
| `src/render.ts` | The human-readable report. Every claim the tool makes out loud is phrased here. |
| `src/discover.ts` | Deriving a config entry from an installed Homebrew formula. |
| `src/exec.ts` | The one `execFile` wrapper. Closes the child's stdin so a bare-probed REPL exits instead of waiting. |
| `src/types.ts` | Shared shapes. Read this first. |

## The rule this project actually runs on

**Never state a conclusion the code did not reach.** Most of the bugs fixed
here have been the same one wearing different clothes: a green "up to date"
for a repo that published nothing comparable, an "affects you: none" over a
directory that does not exist, an engine named in the footer that was never
contacted, an exact count taken from a page that had been cut short.

Practically, that means: when a check cannot be performed, say so as its own
state. Do not fold it into the reassuring answer. `render.ts` has separate
branches for "unknown", "no engine", "engine said nothing" and "digest
failed" for exactly this reason — and if you add a code path that can fail
quietly, it needs its own branch too.

## Tests

`node:test`, no framework. `pnpm test` runs everything in `test/`.

- A test's name should state the behaviour, not the function
  (`"a forge with no comparable release is reported unknown, never up to
  date"`).
- Where a test exists because something was wrong once, say so in a comment
  with the real case — `neovim publishes a rolling stable release alongside
  v0.12.4, both with "prerelease": false`. Those comments are why the test is
  not deleted as redundant three years from now.
- Shelling out is fine and often the point: `test/probe.test.ts` writes real
  fixture binaries, because "prints its version to stderr" and "exits 1 but
  printed it anyway" cannot be faked usefully.
- `fetch` gets stubbed for forge and engine tests (`test/sources.test.ts`,
  `test/engine.test.ts`). No test may touch the network.
- Assert the discriminating value, not a superset. `assert.match(out,
  /unknown/)` alone would pass on output that also says "up to date" — pair
  it with `assert.doesNotMatch`.

CI runs `check`, `lint` and `test` on Linux and macOS. macOS is not
redundant: `add`/`scan` are built on brew, the launcher resolves symlinks in
POSIX `sh` without GNU `readlink`, and the usage verdict shells out to grep.

## Public contracts

Changing any of these is a breaking change and belongs in its own PR with the
box in the template unticked and an explanation:

- **Exit codes** — `0` nothing pending, `1` updates available, `2` error.
  Under `--yes`: `0` every update ran, `2` any failed.
- **`--json` shape** — `{ engine: { kind, model, label }, missingUsagePaths,
  reports[] }`.
- **Config format** — `usagePaths`, and `tools[].{ name, source, version: {
  cmd, match }, update }`. Unknown keys are preserved on write, so adding one
  is safe; renaming or removing one is not.
- **Existing `version.match` patterns** — configs in the wild hold regexes
  generated by earlier versions. `confirmProbe` may generate better ones, but
  `installedVersion` has to keep resolving the old ones.
- **Source forms** — `github:owner/repo`, `codeberg:owner/repo`, full forge
  URL.
- **No runtime dependencies.** Nothing outside Node's standard library is
  imported at runtime, and there is no build step. A PR that adds either
  needs to argue for it first, in an issue.

## Filing a good issue

The forms ask for particular evidence because it is what separates two
different fixes, not to make reporting tedious:

| Form | Asks for | Because |
| --- | --- | --- |
| Wrong installed version | Whether the entry came from `add` or your own hand, plus the binary's raw output | A generated entry that is wrong is a bug in `confirmProbe`; a hand-written one usually needs a better regex — different fixes, different files. |
| Wrong update status | `--json --no-judge`, and the project's real tag names | `--no-judge` removes the model from the picture. Tag shape is behind most wrong answers: `jq-1.8.2`, a rolling `stable`, `b10141`. |
| Wrong digest or verdict | Whether grep finds the extracted string yourself | Found by grep but not reported means `usage.ts` is wrong. Not found by either means the model extracted a string nobody writes, and the prompt is wrong. |
| `add` / `scan` | `brew info --json=v2` for the formula | If brew holds no forge URL, declining is correct behaviour. If it does and we missed it, `sourceFromUrls` is wrong. |
| Crash | Whether it happens for every tool or one | Splits the shared path from one entry's data. |

## Commits and PRs

Commit messages say why, not what — the diff already says what. Present
tense, lower case subject, no trailers.

Fill in the PR template's Claims section properly: one bullet per
user-visible change, phrased so a reviewer can check it against the diff. It
is the difference between a review that takes ten minutes and one that takes
an hour.
